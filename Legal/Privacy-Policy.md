# Quality Scorecard for Jira — Privacy Policy

**Effective Date:** March 7, 2026
**Last Updated:** October 25, 2026
**Version:** 1.4

## 1. Introduction

This Privacy Policy describes how Nexus Frontier ("we," "us," or "our") collects, uses, stores, and protects information through the Quality Scorecard for Jira application ("the App"), a Jira Cloud app available on the Atlassian Marketplace.

Quality Scorecard for Jira is a quality assurance and ticket evaluation management tool that operates entirely within the Atlassian Forge platform. We are committed to protecting the privacy of our users and complying with applicable data protection laws, including the General Data Protection Regulation (GDPR) and the California Consumer Privacy Act (CCPA).

By installing or using Quality Scorecard for Jira, you acknowledge that you have read and understood this Privacy Policy.

---

## 2. Data Controller and Data Processor

- **Data Controller:** The organization ("Customer") that installs and administers Quality Scorecard for Jira on their Atlassian Jira Cloud instance is the Data Controller for End-User Data processed through the App.
- **Data Processor:** Nexus Frontier acts as a Data Processor, processing End-User Data on behalf of the Customer in accordance with this Privacy Policy and our Data Processing Agreement (DPA).
- **Sub-processor:** Atlassian Pty Ltd is a sub-processor, as all App data is stored within Atlassian's Forge infrastructure.

## 3. Data We Collect

### 3.1 Data Collected from Jira

The App accesses the following data from the Customer's Jira Cloud instance through Atlassian-provided APIs:

| Data Type | Fields | Purpose |
|-----------|--------|---------|
| **User Identity** | Account ID, Display Name | Identify evaluators, assignees, and administrators |
| **User Email** | Email Address | Read from the Jira "myself" endpoint only as a last-resort fallback for the current user's display name; never stored and never shown to other users |
| **User Avatar** | Avatar URL | Display user profile images in the App UI (not stored) |
| **User Permissions** | Result of Jira permission checks (`ADMINISTER`, `BROWSE_PROJECTS`) | Determine administrator privileges and project visibility |
| **User Groups** | Group Memberships | Only if the Customer configures an optional administrator group; otherwise not read |
| **Issue Data** | Issue Key, Summary, Status, Priority, Type, Assignee, Reporter, Project, Created Date, Updated Date, Resolution Date | Display ticket context for evaluations and analytics (read at display time, cached in the browser, not stored server-side) |
| **Project Data** | Project Key, Name, Avatar URL | Configure allowed projects for evaluation |

### 3.2 Data Generated by the App

The App creates and stores the following data through user interactions:

| Data Type | Description | Contains Personal Data |
|-----------|-------------|----------------------|
| **Ticket Evaluations** | Quality scores, free-text feedback, evaluator identity, timestamps (stored per site and per project) | Yes (evaluator Account ID, Display Name; any personal data an evaluator types into feedback) |
| **Display Name Caches** | Caches linking Account IDs to Display Names (manual overrides and automatically resolved names) | Yes |
| **Role Definitions and Assignments** | Roles per project and user-to-role mappings (RBAC) | Yes (Account IDs in assignments) |
| **Audit Logs** | Records of denied access attempts, role/permission changes, evaluation deletions and personal-data erasures | Yes (Account IDs) |
| **Project Access Configuration** | List of projects enabled for evaluation, including who added or removed them | Yes (Account IDs, Display Names) |
| **Coverage Targets** | Quality coverage target percentages | No |
| **Evaluation Criteria** | Scoring criteria definitions | No |
| **User Preferences** | Theme selection (light/dark), selected project, tickets hidden from the Missing Evaluations list | No |
| **Personal Data Index** | List of Account IDs for which the App holds data, with last-refresh timestamps (used for Personal Data Reporting, Section 7.3) | Yes (Account IDs) |

The App does not collect IP addresses, device identifiers, usage analytics or request counts.

### 3.3 Client-Side Data

The App temporarily caches data in the user's browser to improve performance:

| Storage Type | Data | Retention |
|--------------|------|-----------|
| **IndexedDB** (`qc-persisted-cache`) | Advanced analytics results, ticket metadata | 30 minutes to 2 hours (entries past their TTL are ignored and overwritten) |
| **In-Memory Cache** | Evaluations, analytics, user display names, criteria | 1 minute to 2 hours (cleared when the page is closed) |

Client-side caches are stored only in the individual user's browser and are not transmitted to any external service.

## 5. Where Data Is Stored

### 5.1 Server-Side Storage

All server-side data is stored in **Atlassian Forge Key-Value Storage**, which is:

- Hosted and managed entirely by Atlassian within their cloud infrastructure
- Encrypted at rest using AES-256 encryption
- Encrypted in transit using TLS 1.2 or higher
- Subject to Atlassian's own security and compliance certifications (SOC 2, ISO 27001, ISO 27018)
- Isolated per app and per Jira site (multi-tenant isolation)

Quality Scorecard for Jira does **not** store any data on servers owned or operated by Nexus Frontier.

### 5.2 Client-Side Storage

Temporary caches are stored in the user's browser (IndexedDB and in-memory) and remain on the user's device. These caches expire automatically and can be cleared by the user at any time through standard browser controls.

### 5.3 Data Residency

Because all data is stored within Atlassian Forge infrastructure, data residency is governed by Atlassian's own data residency policies. Quality Scorecard for Jira does not independently control or offer data residency selection. Please refer to [Atlassian's Data Residency documentation](https://support.atlassian.com/security-and-access-policies/docs/understand-data-residency/) for details on where your data is stored.

## 7. Data Retention

### 7.1 Retention Periods

The App does not apply automatic, time-based expiry to the data it stores. Data is retained for as long as the Customer keeps the App installed, unless it is removed through one of the mechanisms below. The Customer, as Data Controller, decides when evaluation data is no longer needed.

| Data Category | Retained until | Removal mechanism |
|---------------|---------------|-------------------|
| Ticket Evaluations | Deleted by an authorised user, erased after account closure, or App uninstalled | "Delete Evaluations" permission in the App; Personal Data Reporting (Section 7.3); uninstall |
| Display Name Caches | Account closure or uninstall; server-side user caches are refreshed after 1 hour (user info) / 24 hours (project user lists) | Personal Data Reporting; uninstall |
| Role Definitions and Assignments | Changed by an administrator or App uninstalled | Settings → Roles & Access; uninstall |
| Audit Logs | App uninstalled | Uninstall (a 90-day retention is planned but not yet enforced) |
| Project Access Configuration, Coverage Targets, Evaluation Criteria, User Preferences | Changed by a user/administrator or App uninstalled | In-App settings; uninstall |
| Personal Data Index | Account closure or uninstall | Personal Data Reporting; uninstall |
| Client-side caches | 1 minute – 2 hours | Automatic expiry; browser storage controls |

### 7.2 Data After Uninstallation

When Quality Scorecard for Jira is uninstalled from a Jira Cloud site, all data stored in Forge Key-Value Storage for that installation is handled according to Atlassian's standard Forge data lifecycle. Atlassian's platform retains uninstalled app data for up to **28 days** as a soft-delete grace period — during which the data is inaccessible to the app but recoverable if the customer reinstalls the app within 21 days. After 28 days, all data is permanently deleted by the Atlassian platform.

Quality Scorecard for Jira does not independently retain or extend this retention period. We do not maintain any data store outside of Atlassian Forge.

Client-side caches (IndexedDB) will persist in individual browsers until manually cleared or until the cached entries expire.

Reference: [Atlassian Forge Data lifecycle for hosted storage](https://developer.atlassian.com/platform/forge/storage-reference/hosted-storage-data-lifecycle/).

### 7.3 Personal Data Reporting to Atlassian

In addition to the in-app data subject rights described in Section 8, Quality Scorecard for Jira implements Atlassian's **Personal Data Reporting API** as required for Marketplace cloud apps that store user personal data. On a weekly cadence, the App reports to Atlassian the list of Atlassian Account IDs for which it currently stores personal data, along with the timestamp at which each user's data was last refreshed.

When Atlassian indicates that an account has been **closed**, the App automatically erases that user's evaluations from the site-wide evaluation list, removes the user's display-name override and personal-data index entry, and records the erasure in the audit log. When Atlassian indicates that an account's data has been **updated**, the App refreshes the cached display name from the Atlassian user APIs.

Residual references to a closed account may remain in project-scoped evaluation lists, role assignments, automatically resolved name caches and audit entries until removed by Nexus Frontier on request (Section 8.7) or until the App is uninstalled. We are extending the automatic erasure to cover these locations in a future release.

This mechanism complements — and does not replace — the data subject rights below. Reference: [Atlassian user privacy guide for app developers](https://developer.atlassian.com/platform/forge/user-privacy-guidelines/).

## 8. Data Subject Rights (GDPR)

The App supports the exercise of data subject rights through a combination of in-App functions available to the Customer's administrators and assistance from Nexus Frontier as Data Processor. There is no self-service "export my data" or "delete my data" button for individual end users; requests are handled through the Customer's Jira administrator.

### 8.1 Right of Access (Article 15) and Data Portability (Article 20)

Administrators can export all evaluations (including evaluator identity, scores, feedback and timestamps) from the App's dashboards in CSV or Excel format and filter them for a given user. Role assignments and project access history are visible under Settings. For a complete compilation covering audit entries and caches, contact Nexus Frontier (Section 8.7); we provide the data in a structured, machine-readable format.

### 8.2 Right to Erasure (Article 17)

- **Automatic:** when an Atlassian account is closed, the App erases the user's evaluations from the site-wide list and removes cached names and index entries (Section 7.3).
- **Administrator-initiated:** users with the "Delete Evaluations" permission can delete all evaluations of a given ticket; administrators can remove a user's role assignments.
- **Processor-assisted:** for complete erasure of a specific user's data (all evaluations they authored, residual caches, role assignments and audit references), the Customer's administrator contacts Nexus Frontier (Section 8.7). We perform the erasure within the Customer's Forge storage and confirm completion.
- **Uninstall:** removing the App deletes all App data for the site (Section 7.2).

### 8.3 Right to Rectification (Article 16)

Display names are sourced from Jira user profiles. To correct a display name, users should update their Jira profile; the App picks up the change on its next name refresh (including through Personal Data Reporting "updated" signals). Scores and feedback can be corrected by saving a new evaluation, which supersedes the previous one in all analytics.

### 8.4 Right to Object (Article 21) and Restriction of Processing (Article 18)

Users may object to processing by contacting their organization's Jira administrator, who can remove the user's role assignments (stopping further evaluation activity attributed to them) and request erasure as described above.

### 8.5 How to Exercise Your Rights

Data subject requests should be directed to your organization's Jira administrator in the first instance. For requests that require Nexus Frontier's assistance, the administrator contacts **support@nexusfrontier.net** with the subject line "Quality Scorecard for Jira — Data Subject Request", the Jira Cloud site URL and the Atlassian Account ID concerned. We respond within the timeframes set out in the [Data Processing Agreement](./Data-Processing-Agreement.md) and in any event within 30 days.

## 10. Security Measures

We implement the following measures to protect data:

| Measure | Implementation |
|---------|----------------|
| **Encryption at Rest** | AES-256 via Atlassian Forge infrastructure |
| **Encryption in Transit** | TLS 1.2+ for all communications |
| **Authentication** | Handled natively by Atlassian Forge — no separate credentials required |
| **Authorization** | Role-based access control (RBAC) with per-project granularity, enforced server-side in every backend function; generic storage access limited to an explicit allow-list of keys |
| **Input Validation** | Backend validation of JQL, project keys, issue ids, account ids, storage keys and pagination; CSV formula-injection prevention on export; React output encoding |
| **Abuse Protection** | Client-side request limiting (max 8 concurrent calls, request de-duplication) plus Atlassian's platform-level Forge and Jira API rate limits. The App does not implement its own per-user rate limiter. |
| **Audit Logging** | Denied access attempts, role/permission changes, evaluation deletions and personal-data erasures are logged with timestamps and user identifiers |
| **Least Privilege** | App requests only the minimum Jira API scopes required: `read:jira-work`, `read:jira-user`, `storage:app`, `report:personal-data` — no write access to Jira |
| **No External Egress** | No data is sent outside Atlassian's infrastructure |
| **No Hardcoded Secrets** | No API keys, tokens, or credentials in source code |

For full security details, see our [Cloud Security Statement](./Cloud-Security-Statement.md).

## 16. Jira API Scope Justification

Quality Scorecard for Jira requests the following Atlassian API scopes, each with a specific, limited purpose:

| Scope | Purpose |
|-------|---------|
| `read:jira-work` | Read issue data (key, summary, status, priority, type, assignee, reporter, dates), project data and the user's own Jira permissions for evaluation context, analytics and access checks |
| `storage:app` | Store and retrieve evaluation data, criteria, roles, audit logs, and user preferences in Forge Key-Value Storage |
| `read:jira-user` | Read user Account IDs and Display Names (and group memberships only when an optional administrator group is configured) for user identification and administrator verification |
| `report:personal-data` | Required by Atlassian's Personal Data Reporting API. Allows the App to report to Atlassian, on a weekly schedule, the list of Account IDs for which it stores personal data so Atlassian can notify the App when accounts are closed or updated. See Section 7.3. |

The App does not request `write:jira-work` or any other write scope. Earlier versions requested `write:jira-work` without using it; the scope was removed during the 2026 security hardening.
